# RAG存储架构
关键在于向量和原始切片以及原始文件 怎么存储：1. 分离式 2. 一体式3.混合式
## 分离式
1. 使用**MySQL/PostgreSQL**来存储原始切片元数据(存：文档 ID、标题、作者、时间、来源、分块 ID、权限、标签、状态等)
2. 使用**专用向量库**（Milvus、Weaviate等）存储向量数据，切片ID，切片原文，以及少量方便过滤的元数据
3. **原始文档**：存 **对象存储**，只存不检索

## 一体式
- **专用向量库内置元数据**：Weaviate/Milvus 自带元数据字段，支持**向量 + 元数据过滤**
-  **Elasticsearch**：存全文 + 向量 + 元数据，做**混合检索**（BM25 + 向量）
-  **PostgreSQL + pgvector插件**：单库存表 + 向量，无需跨库，适合轻量场景

# 海量数据的分布式存储方案
当数据规模到达亿级以上时，需要完全解耦的分布式三部分架构。
1. 元数据存储
	1. MySQL → 分布式 MySQL（ShardingSphere / 云厂商 RDS 分库分表）
	2. 或直接上 TiDB / OceanBase（分布式 NewSQL，天然支持海量行）
2. **向量存储（高维向量 + 相似度检索）
	- Weaviate 集群
	- Qdrant 分布式
	- Milvus 分布式版（最主流）
	-  **向量冷热分离**：
	    - 热数据：SSD 高性能向量集群
	    - 冷数据：压缩 + 对象存储
	- **多级检索**：
	    - 粗排：ES / 向量库
	    - 精排：重排序模型（bge-reranker 等）
3. **原始文档 / 大文件（对象存储）**
	- S3 / 阿里云 OSS / 腾讯云 COS
	- 只存原文，不检索，无限扩容

# 性能优化
## 会出现瓶颈的地方
1. **用户问题 → 向量化（Embedding）** ⏱️ 50-100ms
	1. 本地部署Embedding模型
	2. 缓存高频的热点问题，直接进行全量对比
2. **向量库检索（ANN 检索）** ⏱️ 30-50ms
	1. **向量库本身优化**
		1. 向量库索引更换
		2. 向量库算法更换
		3. 开启批量检索、预加载、内存加载
	2. 检索顺序优化. 先过滤数据，减少向量对比的数据集
	3. 对召回数量进行控制，减少召回的数据的数量
3. **召回太多片段 → 重排序（Rerank）** ⏱️ 100-200ms
	1. 重排序使用具有针对性的小模型
	2. 限制一下上下文长度只给LLM2-5条
	3. 开启流式返回
	4. 简单场景直接rerank排序就行了 （什么是简单场景，怎么判断这是个简单场景不需要使用rerank？）
4. **送入 LLM 做生成** ⏱️ 1000-3000ms（最慢）
	1. ：只给 LLM 最相关 2~5 条，不要塞太多？有意思吗？那我重排序就只要3到5条不就行了
	2. 更快的推理引擎
5. 架构级别优化
	- **多级缓存**：问题 → 召回结果 → LLM 回答，全链路缓存
	- **服务异步化**：Embedding、检索、rerank 并行执行
	- **热点数据放内存**：高频向量、高频元数据内存加载
	- **向量库集群分片**：Milvus / Qdrant 分布式，水平扩容

## 核心问题：新资料进来，怎么保证优先级一致？

1. 权威性分：用「规则引擎」而不是人工写死

权威分不能每条手动算，必须自动化：

```
权威分 = 规则计算

官方文档 → 0.9~1.0
内部知识库 → 0.8
外部权威网站 → 0.7
普通文章 → 0.4
用户生成 → 0.1~0.2
```

**新文档一入库，自动打上 authority_score**

2. 高频关键词匹配分：离线 + 实时双链路

**（1）维护一个「全局高频词库」**

- 从日志里挖：top 1000 / 5000 高频问题
- 定期更新（每天 / 每周）

**（2）新文档进来时，自动计算**

- 与高频词库的 BM25 相似度
- 或简单的词匹配数、权重和
- 结果存入 keyword_match_score

**（3）批量更新（保证全局一致）**

- 每天离线跑任务：对所有文档重新计算关键词分
- 增量更新 MySQL
- 不影响线上

# 质量保证与评估
## 检索质量，检索质量是命根子

prompt的关键指标是什么？
**关键指标**：
- **Recall@k**：前 k 个召回片段中，真正相关的片段占全部相关片段的比例 **数量(有没有漏)**
- **Precision@k**：前 k 个召回片段中，相关片段占比 **质量（召回错了每）**
- **Hit Rate@k**：前 k 个结果至少命中一个相关片段的概率 **命中率（能不能找到用户需要的答案）**
- **MRR（Mean Reciprocal Rank）**：首个相关文档排名的倒数均值，衡量排序合理性 **重排序效果**
- **上下文相关性**：召回片段与 Query 的语义匹配度

## 生成的质量
**关键指标**：
- **Faithfulness（忠实度）**：回答完全基于检索上下文，无幻觉、无编造
- **Factuality（事实准确性）**：回答无事实错误、逻辑错误
- **Answer Relevance（回答相关性）**：紧扣用户问题，不跑题、不冗余
- **Completeness（完整性）**：覆盖问题所有要点
- **Fluency（流畅性）**：语法、逻辑、可读性

## 工程效率
- **检索延迟、生成延迟、端到端耗时**
- **QPS / 吞吐量**
- **向量库召回速度**
- **资源与成本**

# 标准评估方法（工业界主流流程）
  根据搜索结果，以下是工业界RAG评估的真实情况：                                                                                                                      1. 离线自动评估

  检索指标：
  - Recall@k、Precision@k、MRR、Hit Rate@k（衡量召回质量）

  生成质量指标：
  - BLEU：计算 N-gram 重叠率（机器翻译常用，但对意思相同但表述不同的内容判分不准）
  - ROUGE：对比自动总结和参考答案的重叠程度（用于摘要生成）
  - BERTScore：用 BERT 提取句子特征，计算词嵌入相似度（比 BLEU/ROUGE 更好，能捕捉语义）
  - Sentence-BERT：计算句子级别的语义相似度

  忠实度评估：
  - 用 NLI（Natural Language Inference）模型检测上下文蕴含（即回答是否完全基于检索内容）


  2. LLM-as-Judge（最实用）

  原理：用一个更强的 LLM 充当"评委"

  优势：
  - 与人工评估的一致性 >80%
  - 成本低、可规模化（相比人工）
  - 能自动化处理大量样本

  评估维度：忠实度、相关性、事实准确性、完整性 → 输出 1-5 分

  实践发现：LLM 与人工评判效果相当，在 80% 以上的情况下得分完全一致

  ---
  3. 人工评估（金标准）

  适用场景：上线前最终验收、核心场景校验

  做法：
  - 多维度打分表
  - 多人标注 + Kappa 系数（一致性校验）

  特点：最权威，但成本高、速度慢

  ---
  4. 在线 A/B 测试（真实效果）

  对比：原 RAG vs 优化后 RAG

  关键指标（用户真实行为）：
  - 问题解决率
  - 差评率
  - 二次提问率
  - 停留时长

  ---
  5. 幻觉专项评估（核心痛点）

  评估对象：检测 LLM 回答中的编造信息

  方法：
  - 构造事实性/对抗性查询
  - 用 LLM 或 NLI 模型自动判定是否编造
  - 统计幻觉占比和错误类型

  主流工具：
  - MetaRAG：无需标注数据的黑盒幻觉检测
  - FActScore：将长文本分解为原子事实，逐一验证（用 Wikipedia 作知识库）
  - TLM 方法：目前最有效的幻觉检测方法（AUROC 最高）
